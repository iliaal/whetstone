# Performance measurement

Use this procedure before a performance number supports a completion claim or an implementation choice. For a requested ballpark, a single run is acceptable when labeled as such; still verify completed work, failures, and output correctness.

1. **Define the comparison.** State the metric, workload, and timing boundary. Name the objective: behavior as shipped, or behavior under production tuning. Both are valid questions; record each configuration and limit the conclusion to the question measured.
2. **Inspect the harness.** Confirm that the claimed work completes inside the timed region. Await asynchronous operations, consume lazy results, and verify the expected effects. Record expected versus completed work and failures for that region. Check output correctness; fast rejections, skipped work, and unexecuted computations cannot support a speedup claim.
3. **Control the conditions.** Record revisions, build modes, runtime versions, data, concurrency, and cache state that affect the comparison. Measure the current baseline alongside the candidate under comparable conditions. Separate diagnostic profiling from timed runs when instrumentation changes the cost. For native build provenance, layout effects, and unchanged controls, use `ia-c-systems` or the applicable language guidance.
4. **Check the load source.** For generated load, inspect the driver as well as the service. A saturated generator can cap throughput before the service reaches capacity. Bound the claim to the exercised load until generator headroom is established.
5. **Check repeatability.** Interleave comparable baseline and candidate runs to expose drift. Report the run count, central value, and spread for both sides. When variation obscures the effect, report that the evidence does not establish a difference.
6. **Check the scale.** Relate a local saving to the baseline time spent in the changed work and the end-to-end path. Check relevant bandwidth or resource limits. If the gain exceeds the saving that the changed fraction alone could explain, investigate the timing boundary, cache or queue effects, and other affected work. An oversized gain needs explanation; nonlocal effects can be real.
7. **Separate effect from cause.** Report the observed difference and its uncertainty separately from causal attribution. A repeatable, valid comparison may be **measured but unattributed**. An unchecked work or error path cannot support the performance claim. Identify the missing evidence instead of forcing a bottleneck explanation.

Report the bounded claim, comparison objective, configurations, completed work and failures, correctness evidence, run count and spread, and attribution limits. Keep a microbenchmark conclusion local unless an end-to-end measurement supports a broader claim. Success means the reported number measures the claimed correct work and the conclusion stays within the observed conditions.
